# FastDB 0.2.3 release record

The coordinated release uses immutable tag `v0.2.3`, source
`abba785ef2a7d3fbee1bbc608393a3e6c7b042c4`, for Python `fastdb4py`, npm
`fastdb4ts`, Rust `fastdb`/`fastdb-sys` and the Core SDK.

The verified candidate contains 43 tested archives: 35 Python wheels, one sdist,
four Core bundles, two Rust crates and one npm tarball. The original five
Python platforms retain cp310/cp311/cp312/cp313/cp314/cp314t. Native Windows
ARM64 adds cp311/cp312/cp313/cp314/cp314t and an
`aarch64-pc-windows-msvc` Core bundle. NumPy's Windows ARM64 wheels require
Python 3.11+; the original platforms retain Python 3.10 support.

`windows-11-arm` passed native Core/C ABI/Rust tests and every installed
Windows ARM64 wheel's read/write smoke and payload tests before registry
publication. PE machine checks reject x64 binaries mislabeled as ARM64.
The portable format, runtime semantics and ABI-117 remain unchanged.

Release Artifacts builds the candidate once. Publication downloads those
exact-source archives by CI run ID and verifies the complete inventory,
source identity, sizes and SHA-256 hashes. PyPI's tag-push job reuses the
tested `release-part-python`; npm and crates workflows reuse the combined
candidate. No publication job rebuilds packages. Existing trusted publisher
workflow filenames and environments are unchanged.

See [Windows ARM64 preparation](windows-arm64.md) for local checks and the
original 0.2.2 tag's architecture blocker, and [publishing](publishing.md)
for CI reuse and selective backfill behavior. Older tags remain immutable.

## Publication

- [PyPI 39555050453](https://github.com/world-in-progress/fastdb/actions/runs/39555050453) reuses the original exact-source Python artifact.
- [npm 39554620421](https://github.com/world-in-progress/fastdb/actions/runs/39554620421) verifies the public archive and skips upload because the identical version already exists.
- [Rust 39553646480](https://github.com/world-in-progress/fastdb/actions/runs/39553646480) publishes and verifies both tested crates.

The first npm upload was accepted, but npm reported asynchronous processing;
the original one-minute verification window expired before public metadata
appeared. The subsequent verification-only dispatch passed without uploading
again. Future verification polls for up to ten minutes and refreshes registry
metadata. Hash mismatches still fail immediately.

The first tag-triggered PyPI run staged all files but skipped its upload job:
GitHub propagated the deliberately skipped backfill builder through the job
dependency chain. Controller commit `be4e3a0` adds an explicit status condition
and requires successful staging before upload. The manual publish uses the
same trusted publisher, original tag, source and CI artifact. The tag has
not moved. This controller change passed local regression tests and both
[lightweight CI](https://github.com/world-in-progress/fastdb/actions/runs/39555031426)
and [artifact metadata checks](https://github.com/world-in-progress/fastdb/actions/runs/39555031480);
all native, wheel and WASM builders were skipped.

The [GitHub release](https://github.com/world-in-progress/fastdb/releases/tag/v0.2.3)
retains the candidate archives, exact CI manifest and publication receipt.

All 39 public registry files were downloaded and matched the CI manifest by
size and SHA-256: 36 PyPI files, one npm tarball and two Rust crates. The
complete local 43-archive inventory also passed the release verifier.
Additional consumer checks passed against the published bytes:

- Python 3.10 on macOS ARM64 installed `fastdb4py==0.2.3` with
  `--only-binary=:all:` into a fresh environment and passed all 34 payload tests.
- The public npm tarball installed into an isolated consumer and passed the
  package inventory and WASM payload smoke checks without rebuilding WASM.
- A fresh Cargo consumer downloaded both `=0.2.3` crates from crates.io and
  linked the retained macOS ARM64 SDK. Compile/codegen/build/open/view,
  materialization and invalidation checks passed without rebuilding C++ Core.
