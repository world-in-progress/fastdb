# FastDB 0.2.4 release record

The coordinated release uses immutable tag `v0.2.4`, source
`f82fa13adeae2b87a295bf984821c85c44b55a3d`, for Python `fastdb4py`, npm
`fastdb4ts`, Rust `fastdb`/`fastdb-sys` and the Core SDK.

0.2.4 addresses standalone native database ownership, numeric column cache
retention, and mapped backing lifetime. The design, memory measurements and
local validation are in the [native memory report](../reports/0.2.4-native-memory.md).
The verified candidate keeps the 0.2.3 inventory of 43 archives: 35 Python
wheels, one sdist, four Core bundles, two Rust crates and one npm tarball.
Portable payload semantics and ABI-117 are unchanged.

## Exact-source validation

- [Run Tests 40932272066](https://github.com/world-in-progress/fastdb/actions/runs/40932272066): complete success, including sanitizers.
- [Release Artifacts 40932272107](https://github.com/world-in-progress/fastdb/actions/runs/40932272107): complete success; one retained 43-archive candidate. The native Windows x64 and ARM64 jobs each passed 41 C++ tests, including `legacy.lifetime`, and the ABI export check.

Release Artifacts for the version merge `8f24619`
([run 40926228094](https://github.com/world-in-progress/fastdb/actions/runs/40926228094))
failed to compile `tests/cpp/test_legacy_lifetime.cpp` with MSVC. The test
included `windows.h` after private headers that use `namespace std`, so the RPC
`byte` typedef was ambiguous with `std::byte`.
[PR #45](https://github.com/world-in-progress/fastdb/pull/45) defines
`WIN32_LEAN_AND_MEAN`. Pull-request CI does not build native Windows targets,
so the run above is the first Windows compile of the fix.

The combined candidate is artifact `12922534983`; its GitHub ZIP digest is
`sha256:f7cb6fdf7e408d4b282f6baff7ea41001a3315d16fad88d1a14501068262b6bc`.
The exact CI `release-manifest.json` is 13,092 bytes, SHA-256
`8a07ab93409811bb5e11418876ba082594758c2b3b87a766699c447586a9c5bf`.
The Python fragment is artifact `12924197817`. The candidate passed the
release verifier for its source SHA.

## Windows x64 check before publication

A Windows 11 x64 machine installed the candidate CPython 3.10 wheel from this
run into a fresh environment.

- With cyclic GC disabled, six write cycles and six read cycles of a
  15,498,593-row F32 table kept the process commit charge (`PrivateUsage`)
  flat: write cycles changed it by 0 bytes and read cycles by at most 4 KiB.
  The published 0.2.3 wheel grew by 374–379 MiB per write cycle and
  312–317 MiB per read cycle in the same script. Removing the data file after
  the cycles succeeded.
- The full Python suite passed 397 tests and skipped one. The five failures
  are Windows shared-memory defects that also fail with 0.2.3 and its tests:
  - `ObjectEngine.share()` closes its only handle, which deletes a Windows
    named mapping before `ObjectEngine.load` opens it (four tests).
  - `FastSerializer.loads_shm` compares the requested range with the
    page-rounded size of an opened Windows mapping. The out-of-range test
    therefore reaches the native loader, which raises
    `Invalid FastDB database buffer.` instead of the size error; 0.2.3 raised
    `AttributeError` there.

These Windows defects are not regressions and remain open.
