# FastDB 0.2.1 Python wheel backfill preparation

Status: locally validated on 2026-10-16; package upload awaits the maintainer's manual workflow dispatch. Source is the unchanged `v0.2.1` tag at `4f99f86a662b0e950a0dd29800c25a1c9fca4def`. Package sources, versions and the tag are unchanged.

`python-distributions.yml` is shared by Release Artifacts and `pypi_publish.yml`. Its policy selects cp312, cp313, cp314 and cp314t on macOS arm64/x86_64, manylinux x86_64/aarch64, and Windows amd64: 20 wheels plus one sdist. Both Linux architectures build in manylinux_2_28; aarch64 uses `ubuntu-24.04-arm` with an explicit native architecture check. Intel macOS cross-builds on the same `macos-15` arm64 runner image as the arm64 wheels, matching the local validation path, and requires Rosetta execution. See the [cibuildwheel platform documentation](https://cibuildwheel.pypa.io/en/v3.4.0/platforms/#macos-architectures).

Every installed wheel must import fastdb4py, build/read a small payload and pass the existing payload suite. Tests use `{package}` so an old tag's tests are selected even when the controller workflow comes from a newer checkout. The inventory gate checks each Python/ABI/platform slot, the sdist, package metadata, duplicate slots and unexpected files. Missing files block the dependency chain before the OIDC upload job. A source-bound, hashed fragment is rechecked before staging.

The PyPI sdist is `fastdb4py-0.2.1.tar.gz`, 1,063,796 bytes, SHA-256 `c2d2d2db8d764350d3c0824f6beaa0ba636b56a1212cdce5bc6ca30eee781b27`. All 309 archived source files match the tag. Rebuilding the sdist from a clean tag export produced the same 318 member names and byte-identical member contents, including the nine setuptools metadata files. This comparison does not claim identical gzip archive bytes.

All eight missing wheels built from that source. Native arm64 Docker and Intel macOS under `arch -x86_64` each passed the installed-wheel read/write check and 34 payload tests per wheel. The final shared test command was also rerun on all four Intel wheels against a clean tag checkout. The real 20-wheel/sdist inventory passed; the real backfill stage selected exactly those eight missing filenames. Release tooling tests passed 34/34 and actionlint passed. [The local verification manifest](0.2.1-wheel-backfill.json) lists every missing wheel's filename, byte size and SHA-256, plus the source and original CI proof runs.

Local macOS validation used the installed macOS 27.0 SDK with an explicit C++ header search path. Official universal2 Python installers were unpacked and relocated in the ignored local build directory because system framework Pythons were absent. These toolchain adjustments are outside package sources and release policy. The manifest hashes identify the local validation files; the hosted build will record its own artifact hashes.

PyPI initially had no active publisher for this project. With the maintainer's explicit approval, a GitHub publisher was added for `world-in-progress/fastdb`, workflow filename `pypi_publish.yml`, with Environment left empty (PyPI displays “Any”). The publishing workflow filename is retained and its job continues to declare no environment. Only that upload job receives `id-token: write`; no static PyPI token is used.

After committing and pushing these changes to `main`, run:

```bash
gh workflow run pypi_publish.yml --repo world-in-progress/fastdb --ref main -f tag=v0.2.1
```

The same option is available under Actions → Publish to PyPI → Run workflow: choose branch `main` and enter `v0.2.1` as `tag`. The current controller resolves that immutable tag, reuses its successful exact-source main CI proofs, builds the full inventory, compares the published sdist source, then stages only filenames absent from PyPI and uploads with `skip-existing`. Existing cp310/cp311 files remain on PyPI. The current 19 files would become 27 after the eight missing wheels are uploaded. Backfill attestations are disabled because the newer controller SHA differs from the package source SHA.

Normal automatic publication occurs only on a matching `v<version>` tag push after that source's main CI proofs succeed. No push, tag creation, remote workflow trigger or package upload was performed during this local preparation.
